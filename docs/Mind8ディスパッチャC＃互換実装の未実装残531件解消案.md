# Mind8ディスパッチャ C#互換実装の未実装残531件解消案

作成日: 2026-11-19

## 1. 目標と現状

console版の全743命令番号（`0x0010`〜`0x02F6`）のうち、現在の未実装531件を、C#に実処理を持つ「実装済未検証」へ移す。分類の母集団・判定基準・各命令の一覧は[進捗表](./Mind8ディスパッチャC＃互換実装進捗表.md)と[基本サンプル完走までの修正案v2の全console中間コード一覧](./Mind8ディスパッチャC＃互換実装基本サンプル完走までの修正案v2.md)を基準とする。

| 現在の未実装の内訳 | 件数 | 解消の内容 |
| --- | ---: | --- |
| C#登録なし | 516 | 命令番号と正規C関数を対応させ、動作するC#ハンドラーを作成して登録する |
| 登録済みだが `UnDefined` を投げるだけのスタブ | 15 | 既存メソッドを正規C処理に置き換える |
| 合計 | **531** | 743件の全命令番号について実処理を用意する |

内訳のうち15スタブは `0x004B`, `0x0059`, `0x0060`〜`0x0062`, `0x0073`, `0x0083`〜`0x0084`, `0x0089`, `0x008E`〜`0x0094`。対象番号と正規C関数名の照合は全命令一覧で再確認する。

解消後の集計目標は、他の分類を変更しない前提で **未実装0件・実装済未検証666件・実装済検証済77件**。ここでいう実装済未検証は「登録がある」だけではなく、命令の実処理が存在する状態を指す。個別期待値テストを通過した命令は、後で実装済検証済へ分類し直す。

## 2. 基本方針

1. **正規console表を唯一の番号対応元にする。** [正規版 `c_words.tbl`](C:/pmind/kernel/c_words.tbl) と対応するC関数本体を参照し、GUI・CGI・コンパイラ向けの別表を混ぜない。
2. **番号ごとのスタック契約を先に明らかにする。** 引数の積み順、消費・返却ワード数、即値の読取り長、Mコード位置の進み方、データ／リターンスタックへの副作用、エラー時のC側の挙動を記録する。
3. **別名は実処理を共有してよいが、番号ごとの登録・契約を残す。** 似た名前だけを根拠に同じハンドラーへ束ねず、C表の関数対応と副作用が一致する場合に限る。
4. **スタブ、成功形の仮値、無条件no-opで未実装を隠さない。** 例外スタブは実処理へ置換する。予約ダミーだけはC側の空関数が仕様であることを確認した上で、明示的なno-opとして実装する。
5. **実装と検証を別の進捗軸にする。** 今回の到達点は処理本体の実装。テストの成功、全入力互換、全OS互換を主張せず、検証が済んだものだけを別途昇格させる。
6. **未対応環境・異常入力を黙って成功扱いにしない。** .NETのAPIで対応できないOS固有機能は、対象環境と制約を明記し、リポジトリ標準に従って明示的に失敗させる。未定義値や不正なハンドルを適当な既定値へ置き換えない。

## 4. 1命令を実装済未検証へ移す条件

命令番号ごとに、次のすべてを満たした時点で「実装済未検証」とする。

- 正規console表の番号とC関数名が確認され、C#関数配列のその番号に対応ハンドラーが登録されている。
- ハンドラーが `UnDefined` を投げるだけのスタブ、空の仮実装、定数の成功形代入ではなく、その命令に必要な処理を行う。
- C関数の入力・出力スタック、ワード幅、符号、即値消費、ポインター領域、Mコード位置・分岐、メモリ副作用を説明できる。
- 別名の場合は各番号を個別に照合し、C側と同じ関数を呼ぶ別名であることが確認されている。
- OS・ファイル・プロセス等の命令は、API対応、エラー伝播、ハンドル／メモリ解放、対象OSの制約を実装または明記している。
- 一覧のC#実装列・分類・根拠を更新し、531件の未実装カウンターから当該番号を一度だけ除く。

この段階では命令単位の期待値照合テストが未実施でもよい。ただし、メソッドを追加しただけ、全番号を同じ汎用ハンドラーに割り当てただけ、テストで到達しただけでは条件を満たさない。後から命令単位テストが成功した場合に限り「実装済検証済」へ変更する。

## 5. バッチごとの確認と計数

各バッチを小さく保ち、以下を同じ変更単位で行う。

1. 対象 opcode とC側根拠を明記し、依存する共通ヘルパーを特定する。
2. 実処理・番号登録・関連する既存呼出し元を実装する。必要な共通ロジックは既存クラスに沿って共有し、複製したopcode別処理を増やさない。
3. ビルドと既存回帰テストを実行し、既存 fixture の成功や標準出力を壊していないことを確認する。これは対象命令の期待値検証とは区別する。
4. 対象命令ごとに上記の実装条件を確認し、一覧の分類を更新する。テスト未実施の命令は未検証のままにする。
5. 743行の重複・欠落と集計式を確認する。新たに検証済みへ移した命令があれば、未実装数だけでなく未検証／検証済数も同時に更新する。

バッチのサイズは機能の密結合度で決める。分岐とループ、文字列実体と文字列参照、ファイルハンドルとその操作など、単独では意味をなさない機能を分割しすぎない。一方、全OS APIを一度に扱うなど、レビュー不能な大きな一括実装も避ける。

## 6. 主要なリスクと避けるべき近道

- **番号範囲だけを実装済みにする:** 配列長を拡張しただけではハンドラーも処理も存在しない。番号別の登録と実体を確認する。
- **別名を誤って共用する:** 同じC関数名に見えても、スタック効果や返却値が異なる別 opcode がある。根拠なしの一括割当てはしない。
- **OS機能をno-op化する:** ファイル、ソケット、プロセス、DLL/API、同期、レジストリ等は副作用が機能の本体。成功値だけ返す代替を実装完了に数えない。
- **文字列を単なるbyte配列とみなす:** C版の文字数・バイト数、Shift-JIS文字境界、文字列情報、局所スタック参照の違いを保持する。
- **ダミー命令と実機能を混同する:** `0x02F0`〜`0x02F6`の正規C実体は空関数だが、`0x02EF famari`は浮動小数点剰余処理である。連番だからという理由で同じno-opにしない。
- **「テスト61件成功」を531件の検証とみなす:** 既存の61/61はプロジェクト回帰の結果であり、531件の命令単位テストの代わりではない。

## 7. 実装完了時の受入れ条件

- 全console opcode `0x0010`〜`0x02F6` の743番号が正規表と一対一で照合されている（C側の別名を含む）。
- 未実装531件それぞれに対応する登録と実処理があり、例外スタブ・汎用no-op・成功形の仮値が残っていない。ただし正規Cの空関数と確認できる予約ダミーは明示的なno-opでよい。
- 一覧の未実装件数が0で、他カテゴリを含む合計が743のまま。新規に命令単位テストを通したものは、実装済未検証ではなく実装済検証済に数える。
- ビルドと既存回帰テストに成功し、既存fixtureの出力・終了状態に意図しない変更がない。
- 対象OS、未対応のプラットフォーム機能、既知の互換差を完了レポートに明記する。

この受入れは「全命令のC#実処理を用意した」到達点であり、743命令すべてのC版互換を実証したという意味ではない。互換性の確認は、別途命令単位テストとC版との比較を進めて実装済検証済へ移す。
