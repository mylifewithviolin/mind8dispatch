# 互換コンパイラの実装に関するライセンス上の制約

## 結論

`C:\pmind\README.txt` のライセンス条項（README記載のライセンス節、約122行目以降）からは、Mind Version 8 の個人・商用を問わない利用と、対象となるソースコード／オブジェクトコードの改変・再配布が認められていると読めます。また、Mindで開発したアプリケーションについて、開発者が著作権を主張できる旨と、実行時にMindランタイムファイルが必要になる旨が記載されています。

したがって、Mindとの互換性を目指すコンパイラを実装すること自体は、技術面ではMCO形式・命令番号・ランタイムABIを解析し、段階的に実現できます。ライセンス面でも、READMEの文言はMind関連コードの改変・再配布を広く認める方向です。ただし、条項だけでは、互換性を持つ新規コンパイラの全ての実装方法、名称の使用、同梱する全ファイルの権利関係までは確定できません。特に既存ソースを移植する場合は、個々のファイルに適用される権利表示や第三者ライセンスを確認してください。

これは提示されたREADMEの記載に基づく実務上の整理であり、法的助言や、権利者による個別の許諾確認に代わるものではありません。

## READMEから読み取れる範囲

| READMEの記載内容 | 互換実装に関係する意味 |
| --- | --- |
| Mind Version 8 はフリーソフトで、個人利用・商用利用を問わず使用できる | Mindを利用した検証や、商用利用を含むアプリケーション開発を直ちに排除する条項ではない |
| オブジェクトコードとソースコードは自由に改変・再配布できる | 条項の対象となるMindのコードを改変して配布する実装方法を支持する。ただし、同梱物すべてが同じ条件とは限らないため、個別の権利表示も確認する |
| パッケージに含まれるMind関連プログラムとドキュメントには著作権者の表示がある | 著作権表示があることと、READMEが示す改変・再配布の許諾を併せて扱う。表示の削除や、ドキュメント本文の転載を当然に許可されたものと解釈しない |
| Mindコンパイラを使って開発したアプリケーションについて、開発者が著作権を主張できる | 自作アプリケーションとMind本体・ランタイムの権利を区別する必要がある |
| アプリケーションの実行には `mruntNNN` の添付が必要となる旨がある | 生成物の配布では、必要なランタイムを同梱する場合の対象ファイルと適用条件を確認する。アプリケーションの著作権に関する記載だけで、ランタイム単体のライセンス条件まで置き換わるとは扱わない |

## 実装方法ごとの評価

### 1. 独自に実装する（クリーンルーム方式）

公開されているMCOの構造、命令の振る舞い、入出力結果などを観察し、実装コード・コメント・説明文を独自に作成する方法です。既存のMindソースやドキュメント本文をコピーしないため、既存コードの移植より権利範囲を切り分けやすい方法です。

互換性は段階的に広げられます。まずMCOヘッダー、バイト順、命令フェッチ、関数番号表、制御フロー、データ／リターンスタックを実装し、次に基本演算、文字列、配列、入出力、OS依存機能を追加します。出力MCOと実行時ABIの互換性は別々にテストし、C版と同じ入力に対する出力・終了状態を比較するのが適切です。

独自実装であっても、互換であることだけを理由に、Mindの名称・ロゴ・ドキュメント・既存コードの再利用まで許諾されたとは判断できません。配布時の製品名や説明では、公式製品との誤認を避けてください。

### 2. Mindの既存ソースを移植・改変する

READMEの「ソースコードを自由に改変・再配布できる」という記載は、対象となるMindソースを移植して互換実装を作る場合の根拠になります。READMEの適用対象であることを確認したうえで、元の著作権表示・ライセンス文を保持し、改変部分を識別できるようにするのが安全です。

これはクリーンルーム方式とは異なります。既存のCソースを読み、その処理・構造・関数対応を手掛かりにC#へ書き換える場合、実装の進め方としては「独自仕様だけに基づく新規実装」ではなく、「既存実装の移植・翻訳」に近いものです。プログラミング言語を変えても、元ソースの表現や構造に依拠した部分がなくなるとは限りません。そのため、実装者がC#でコードを書いたことだけを理由に、クリーンルーム実装として扱うのは適切ではありません。

一方、READMEの条項はMindのソースコードの改変・再配布を認める旨を含むため、対象ソースをC#へ移植することは、条項が適用される限り、クリーンルーム方式を採らなければ許されないという関係ではありません。むしろ、既存実装を参照して開発できる点が、クリーンルーム方式よりも実装上の近道になり得ます。その代わり、元のソースに由来するコードを含めて配布する場合は、対象ファイルのライセンス条件や表示を引き継ぐ必要性を確認し、独立して新規に書いた部分と区別して管理するのが安全です。条文だけでは、個々の移植コードの法的評価や、すべての同梱ファイルへの許諾範囲までは確定しません。

ただし、READMEの包括的な文言だけから、次のすべてを確定することはできません。

- 互換実装で参照または移植する全ファイルが同じライセンス対象か
- パッケージ内の第三者コード、外部ライブラリ、サンプル、ドキュメントにも同じ許諾が適用されるか
- ソースコードの改変・再配布許諾が、Mindの名称・商標等の使用まで含むか
- ランタイムファイルやリンク済みオブジェクトを個別に再配布するときの条件

したがって、既存ソースからの移植を選ぶ場合は、利用ファイルごとにヘッダー、README、同梱ライセンス、依存ライブラリの条件を確認し、配布物に必要な表示を含めてください。

### 3. 互換コンパイラや生成物を配布する

READMEはMindのソース／オブジェクトコードの改変・再配布を認める記載を含み、Mindで作成したアプリケーションについても開発者の著作権を主張できるとしています。よって、条項の対象範囲を確認したうえでの互換コンパイラ配布や、独自に作成した生成物の配布は、条文と整合する可能性があります。

ただし、次のものは分けてライセンス確認してください。

- 互換コンパイラ自身のソースコードと実行ファイル
- コンパイラが生成するMCO／アプリケーション
- Mindランタイム `mruntNNN`
- リンクされるライブラリやオブジェクトコード
- README、マニュアル、サンプルその他の同梱ファイル

「生成アプリケーションの著作権を主張できる」という記載を、ランタイムやリンク済みライブラリを無条件に自由再配布できる根拠として拡張解釈しないでください。

## 実装を進める際の推奨事項

1. `C:\pmind` の利用対象ファイルを一覧化し、各ファイルの著作権表示・ライセンス・第三者依存を確認する。
2. 既存ソースを移植する箇所と、観察した仕様に基づいて独自に書く箇所を記録する。独自実装では、元ソースやドキュメントの表現をコピーしない。
3. 移植したファイルの著作権・ライセンス表示を保持し、改変箇所を明示する。
4. 生成物の配布時は、Mindランタイムやリンク済みファイルの要否と再配布条件を別途確認する。
5. Mindの名称・ロゴを製品名や公式性の表示に使う前に、商標・表示上の扱いを権利者に確認する。
6. 商用配布、ランタイム同梱、既存ソースの広範な移植を行う場合は、配布対象ファイルの一覧を添えて権利者または法律専門家に確認する。

## 本リポジトリへの適用

本リポジトリは、主にCで実装されたMCO中間コードの実働部分をC#へ書き換え、C版ランタイムとの互換性を目指しています。既存のC実装を参照して対応処理を移しているこのスタイルは、一般にクリーンルーム方式そのものではなく、移植・翻訳を伴う実装として整理するのが妥当です。READMEのソース改変・再配布の条項が対象コードに適用されるなら、クリーンルーム方式を経ずに移植を進める根拠になり得ます。ただし、C#側のコード全体が自動的に同じ条件になる、またはリポジトリに含まれる全ファイルの再配布条件が確定するという意味ではありません。Cソース、C#独自実装、テスト用MCO、ランタイムや外部依存物を分けて、由来と適用条件を確認してください。

進捗の参照先としては、旧「Mind8ディスパッチャ C#互換実装の実装状況」より新しい「Mind8ディスパッチャ C#互換実装 次の優先項目4の完了レポート」を優先します。同レポートではC/C#で同一MCOを実行するhello比較を含む21件のテスト成功が報告されていますが、比較シナリオは限定的であり、全関数・全挙動の互換性を示すものではありません。テスト成功は実装の検証結果であって、ライセンスの適用範囲を確定するものでもありません。
